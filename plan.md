Where to install it: `LinuxAllocationTrace` only acts on `mmap` (`handleSyscall` records the length on entry and holds an ENOMEM return), so nothing else needs a stop. `SECCOMP_RET_TRACE` with no tracer fails the call with ENOSYS. The filter must therefore go only on owned tracees, and they stay traced: `TRACE_OPTIONS` follows fork, vfork, clone and exec, and nothing detaches. Both entry points already stop the tracee before it runs. `adopt` → `replaceParkedChild` injects an `execve`; inject `prctl(PR_SET_NO_NEW_PRIVS)` and `seccomp(SET_MODE_FILTER)` before it. The bootstrap path is seized at its SIGSTOP before `signal(pid, CONTINUE)`. Add `PTRACE_O_TRACESECCOMP` (0x80) to `TRACE_OPTIONS`. On a seccomp stop, resume with `PTRACE_SYSCALL` to catch the exit; after the exit stop, and after every other stop, resume with `PTRACE_CONT`. Measure the split first: compare per-process time for a static and a dynamic image in one rung.

### Frida's injector waits by polling (frida-core `57161b0d`, `lib/base/posix.vala` `ChildProcess.wait_for_next_stop`)

- Every remote call in Frida's Linux injector returns to `DUMMY_RETURN_ADDRESS` (0x320). The call ends in a SIGSEGV stop, which the injector collects with `waitpid(pid, WNOHANG)` on its main loop. It sleeps 0, 1, 2, 5, 10, 20, 50, then 250 ms between polls, and throws `TIMED_OUT` after 5 s. That accounts for the page-fault stops of both rungs' held pairs. It also sets x64's per-process cost: one injection makes several remote calls, each of which can wait up to 250 ms, which matches about 4 processes a second. The preload library (plan step 3, second half) removes this cost for every dynamic image.
- ARM rerun `41764563038` reproduced the deadlock: the subshell 25043 was held at the dummy return, and its child `uname -X` 25055 was held after `execve`. The log went quiet at 03:07:21Z, the moment attempt 13 closed. Again every Frida thread idled in `ppoll`, and the coordinator slept with 69 s of CPU in 75 minutes. Frida must have lost the stop, timed out, and abandoned the tracee, so no child-added event was ever emitted. Any thread of the tracer's thread group can consume a tracee's stop with `waitpid(-1)` unless it passes `__WNOTHREAD`. The scheduler's own `waitpid(-1)` callers pass it (`LinuxAllocationTrace`), or run only in supervisor JVMs (`LinuxProcessTree`). ### Root cause of the rung 1 hangs: Frida leaks a seized fork child when re-injection fails (2026-11-04)

- x64 run `41770178077` (commit `618f12ef9a`) deadlocked the same way, and its report names the tracer. `configure` subshell 29052 stayed in a ptrace stop at a page fault through all five reports, with `TracerPid` 21847. That thread is "Thread-0" of the scheduler JVM 21818: Frida's own `run_main_loop`, idle in `ppoll`. The child has one new thread (29055) polling.
- Mechanism, from frida-core `src/linux/frida-helper-backend.vala`, identical at `57161b0d` and at upstream `main` on 2026-10-29 (release 17.25.2):
  - When a process carrying a Frida agent forks, the child's agent asks the host to `recreate_injectee_thread`. `RejuvenateTask.run` then opens an `InjectSession` (ptrace seize) and calls `rejuvenate`. That launches the loader with a remote call ending at `DUMMY_RETURN_ADDRESS`, then waits 5 s for the new agent thread to connect.
  - `session.close()` (`PTRACE_DETACH`) runs only on success; there is no `finally`. On the 5 s `PROCESS_NOT_RESPONDING` path, `establish_connection` was given the outer `cancellable`, so its `accept_async` stays pending. That keeps the session alive and never disposed. The tracee stays stopped at the dummy return for good, and no child-added event is emitted.
  - The scheduler cannot see or resume it: the hold belongs to Frida's helper, not to child gating.
- The same per-fork rejuvenation, at up to 250 ms per remote-call poll, is the x64 per-process cost.
- Consequence: per-process Frida injection cannot finish a `configure`-heavy build script reliably. The preload library (next deliverable below) removes Frida from dynamic images and with it both the hang and the cost. Until then, rungs that run build scripts with `configure` (jemalloc, aws-lc, openssl) cannot pass. Not done: reporting the leak upstream to frida-core, which is an outward-facing action that needs the user's approval.

### Fix under test: the Cargo producer's images go to the ptrace owner (2026-11-04)

- `LinuxCargoImages` now hands every image that Cargo starts to `LinuxAllocationTrace.Images`, dynamic ones included: build scripts and all their descendants. Before, only static images went there.
- A Cargo wrapper started under a traced image is detached at its exec stop (`Images.detach`, `PTRACE_DETACH`). The compiler attempts it forks then stay untraced and get their own Frida attachment as before. `advance` treats the owner as active once its root is armed by either owner (`admitsChildrenOfNativeRoot`).
- Trade-off, allowed by contract item 3: a denied allocation in a producer image is reported and ends the build, instead of waiting in-process as the Frida malloc hook did. Static images already worked this way. Compiler attempts are unchanged and keep Frida, with in-process waits and token mediation.

  - Tests: `LinuxAllocationTraceNativeTest` covers `filtersStaticImage`, `runsChildOfFilteredStaticImage` and `reportsDenialInFilteredStaticImage`.
  - ARM rung 1 on `0b96ebaf27` passed in 24m 47s, so the ARM injection path works. The preload library is still needed for compiler attempts. Its scope shrinks to the attempt side (allocation hook and token mediation).

### Next deliverable: preloaded native hook library (plan step 3, second half)

Step 3's first half is pushed (`e217e0e850`, `LinuxFridaDevice`): one Frida device manager per Linux Cargo build, borrowed by the leader and every attempt. The second half replaces per-process Frida script injection with a preloaded library. Findings so far:

- rustc 1.95 links jemalloc into the executable with unprefixed `malloc` symbols (see the jemalloc note in [build-scheduler-investigation.md](docs/build-scheduler-investigation.md:203)), so a preload cannot replace `malloc` by symbol interposition; it must patch the resolved global `malloc` in place, as `linux-allocation-hook.js` does today with `Module.getGlobalExportByName('malloc')`.
- Local probe (Linux x64, not committed; source in `.cat/sessions/4b09bd88-09d5-4f88-a2e1-386262e30cc1/temp/gum-devkit-wSrszR/p/{app.c,hook.c}`): a shared library linking the official `frida-gum-devkit-17.24.3-linux-x86_64.tar.xz` (SHA-256 `d5ffd59ebc5f50535e5f5e9c04cd968e2876eb91aff40872fe5afaf56d02a886`) statically, with all symbols hidden by a `{ local: *; };` version script, calls `gum_init_embedded()` and `gum_interceptor_attach` on `gum_module_find_global_export_by_name("malloc")` from its constructor. Under `LD_PRELOAD` it attached to an executable-exported `malloc` before `main`, observed every call and observed a forced NULL return. Added startup cost: about 3–4 ms per process (5.4 ms versus 1.4 ms over 50 runs), against the measured 2.41 s per-attempt start today. The library is 22 MB unstripped.
- Not yet decided or tested: the control channel between the preloaded library and the scheduler (replacing Frida script `send`/`recv`; the C wrapper's existing length-framed socket protocol is the natural transport), how the scheduler authenticates a library instance to an attempt (pid, start time, cgroup), the Cargo token hooks (`linux-cargo-tokens.js` read/write mediation) in C, preserving the allocation-wait registry semantics of `linux-allocation-hook.js` (eight slots, publish/grant identities, sticky fault), behavior across `fork` and `exec` (the preload is inherited through the environment; a statically linked image ignores it and keeps the ptrace path in `LinuxAllocationTrace.Images`), and packaging/pinning the gum devkit in `PrepareReleaseSchedulerNative`.
- Scope after the ptrace move: producer images (build scripts and their tools) already run under `LinuxAllocationTrace`, so the library serves compiler attempts only: every dynamic image that starts inside an attempt's cgroup.
- Contract (Linux, draft 2026-11-04; implement with red tests first, keeping the Frida path until the preload path passes natively):
  - Loading: the scheduler adds `LD_PRELOAD=<library>` and `CODEX_BUILD_HOOK=<socket path>` to the attempt by sending them with `release`. The C wrapper's child sets both before it execs rustc. The library's constructor attaches the `malloc` hook (and the `read`/`write` hooks when `CODEX_BUILD_HOOK_FIFO` names the jobserver FIFO as `major:minor:inode`). It then connects and waits for `welcome` before returning, so `main` never runs unhooked. Allocations made by `ld.so` and by constructors that run before ours are not covered; a NULL from one of them reaches the program as today without a hook.
  - Identity: the server reads `SO_PEERCRED` and accepts the connection only when that PID's `/proc/<pid>/cgroup` is the attempt's cgroup and the client's `hello` carries the same PID and start time (field 22 of `/proc/<pid>/stat`). It replies `welcome` with a fresh installation number. A connection from any other process is closed without a reply, and the client exits 125.
  - Wire: the C wrapper's framing, NUL-separated fields in 4-byte length frames, protocol version 1. Client to server: `hello pid start`; `blocked wait thread bytes errno`; `transfer sequence read|write [byte]`; `granted wait unknown|accepted|duplicate`; `failure cause`. Server to client: `welcome installation`; `grant wait`; `token sequence [byte]`. One hook thread per process reads the socket; a blocked thread waits on its slot.
  - Allocation waits keep `linux-allocation-hook.js`'s semantics: eight slots, issued wait numbers, publish then grant, retry on grant, and a sticky fault that parks every waiter. Publication is immediate (condition variable to the hook thread) instead of the script's 10 ms timer.
  - Token mediation keeps `linux-cargo-tokens.js`'s semantics: a one-byte `read` or `write` on the jobserver FIFO is sent as `transfer` and blocks until its `token`; any other count, or a descriptor whose metadata cannot be read, reports `failure` and parks.
  - Fork: a `pthread_atfork` child handler resets the registry and drops the inherited socket; the child connects as a new installation on its first denial. `posix_spawn` and `vfork` run no handlers; their child execs at once and loads the library again.
  - Exec: the hook intercepts the `exec` family and `posix_spawn`, and puts back `LD_PRELOAD` and `CODEX_BUILD_HOOK` when the new environment drops them. A static target (no `PT_INTERP`) is announced with `exec-static path`. The server replies `adopt`, the client stops itself with `SIGSTOP`, and `LinuxAllocationTrace.Images` seizes it, as the Frida gate's handoff does today. A setuid target fails the attempt.
  - Failure: a lost connection, a malformed frame or any server `failure` parks every hooked call; the server ends the attempt with `cgroup.kill`. The client never retries a connection.
  - Packaging: link the pinned gum devkit statically with every symbol hidden. Build and pin it in `PrepareReleaseSchedulerNative`, x64 and ARM.
  - Open: whether a scan of `cgroup.procs` is also needed to catch a dynamic image that loads without the library (`LD_PRELOAD` ignored for secure-execution images, or a custom loader). Decide after the first native run.
- Implemented: `linux-build-hook.c` with hello/welcome, held `malloc` waits with grants and duplicates, fork, jobserver token mediation (`d89fba2fd8`) and environment restoration across exec. ## Scheduler contract

Cargo and Bazel scheduling must work on Linux, macOS and Windows across the six release targets. A platform feasibility gap leaves the affected acceptance unmet; it does not authorize reduced coverage.

1. Use each build tool's default concurrency as the starting point, subject to estimated-memory admission. When the scheduler runs, it has no fixed job cap: Cargo receives one jobserver slot per CPU and memory admission decides how many run. Keep local resource controls separate from remote execution capacity. Reserve OS headroom and the expected remaining growth of running work; refuse admission beyond the available budget. Learn best-effort estimates from observed demand, and measure unknown work conservatively before raising concurrency.
2. Disable swap/pagefiles where native control is verified; otherwise monitor effective state and growth. Estimated-memory admission applies in both modes. Native low-memory/pressure, growing swap, artificial commit/address-space denial, allocation waits and simple swap occupancy establish different facts and require their own evidence.
3. Inject allocation observation so an actual denied allocation is held and reported to the Java scheduler. Prefer safe continuation when memory permits and it avoids repeated work; terminating/reaping the failed attempt and retrying the action in a fresh process is also allowed. Same-process retry is not mandatory. Continue held allocations oldest-wait-first; fresh retries keep their original action position. Both precede new admission.
4. During recovery stop admissions, retain the oldest running job, and terminate the newest unfinished work when swap grows even if native low-memory remains false. Reap the whole selected tree before reassessment. Retained memory may require terminating selected unfinished work, but preserve valid completed outputs. Occupancy alone cannot drive repeated kills. End recovery on a non-growing sample without native pressure, considering available memory and paging activity. A sole action exceeding capacity must report a terminal limitation instead of entering a futile retry loop.
5. Use supported producer/action interfaces for admission. Linux Cargo registration authenticates the retained current parent/birth, containment, credentials, executable and first held EXEC image before the manager's sole resume. Historical spawn-call attribution is not required. Windows imports authenticated handles; foreign numeric handle values are insufficient. Cover build scripts, linker children, descendants and nested Cargo as well as rustc. Keep the outer Cargo slot across retries, reconcile descendant tokens and partial close, and accept normal wrapper exit after its final response. Never invent a replacement for a lost jobserver token. Changing an existing parent's environment does not alter Cargo's active job limit.
6. Bazel requires actual action identity, admission, result/wait authority and replay authority. Helper/wrapper results cannot substitute for action results; root instrumentation cannot prove action/helper interception. Exercise real compiler, linker, build-script and generator paths, relevant sandbox variants, ordinary failure propagation, including the retained failure-23 action check with its authentic status, and warm-work exclusion. Promote only successful validated action outputs.
7. Require complete authenticated memory batches with valid process, containment and namespace authority. Missing, stale, substituted or partial observations freeze admission/resumption and preserve queue order, accepted history and cumulative activity. Only a fresh accepted complete batch restores eligibility. Accept measurements before advancing history/control; control failure does not erase an accepted batch. Preserve actual operational and cleanup causes and uncertain ownership rather than classifying them by error-message matching.
8. Establish containment before release; preserve original caller streams, binary contents, open-file descriptions, offsets and borrowed lifetimes. Partial stream installation must terminate the unreleased target instead of blindly retrying installation. Whole-tree extinction governs collection and successful result acceptance, not root exit alone. Extinction precedes instrumentation destruction and resource release. Retain authentic root/descendant outcomes, uncertain release/recovery handles and original errors until reconciliation. Controller death must stop and reap the workload. A supported successor invocation must obtain fresh authority and resume safely with retained outer groups and attempt storage; reconcile stale resources where they obstruct that outcome. Diagnostic observer/client removal does not prove safe production resumption. Normal descriptor-closing macOS execution remains required; descriptor-inheriting controls do not pass it.
9. Keep the scheduler outside an action's memory-failure boundary. Distinguish memory failure from ordinary compiler failure; ordinary errors propagate without memory retries. Failed partial outputs do not become completed work. Native checks must establish effective swap state, actual allocation interception, failure classification, ordered recovery, controller survival, whole-tree cleanup, useful outputs and completed-work reuse on each required integration.
